## Context

动机见 `proposal.md - Why`。这里只记录影响技术选型的现状与约束。

**现状**

- 编排层：`AiOpsService` 使用 Spring AI Alibaba 的 `SupervisorAgent` 调度 `plannerAgent` 与 `executorAgent`，两者均为 `ReactAgent`，提示词以硬编码字符串拼装，无任何项目维度变量。
- 工具层：`QueryMetricsTools`（Prometheus）、`QueryLogsTools`（腾讯云 CLS）、`InternalDocsTools`（Milvus RAG）、`DateTimeTools`。工具方法签名不含项目参数，数据源地址由 `application.yml` 全局单值配置（`prometheus.base-url`、`cls.topic-id`）。
- 知识层：Milvus 单集合，文档无归属元数据，检索为全局 top-k。
- 监控层：`HostMetricsCollector` 通过 Oshi 采集本机 CPU / 内存 / 磁盘，经 Micrometer 暴露给 Prometheus；`ClsLogShippingService` 把同样的主机指标定时投递到 CLS。`AiOpsDashboardService` 直接产出单层仪表盘数据。
- 双模开关：`prometheus.mock-enabled` 与 `cls.mock-enabled` 控制真实/模拟数据源，`QueryLogsTools` 在 mock 关闭时不注册为 Bean，改由 MCP 通道提供。

**约束**

- 主机资源在被监控项目之间物理共享，采集必须全局唯一一份，不能按项目重复采集。
- 项目标识由服务端权威解析，不能信任模型自行推断的数据源地址。
- 演示需在单台开发机上完成，被监控项目必须轻量。
- 现有 mock / 真实双模不能被破坏，评测与演示需要可切换。

## Goals / Non-Goals

**Goals**

- 单进程承载多项目诊断，项目边界由服务端强制，而非依赖模型自觉。
- 编排图与工具接口保持单一实现，项目差异全部下沉为配置与提示词变量。
- 平台层与项目层的数据、知识、提示词、报告模板互不污染。
- 故障场景可复现、可撤销、可判定，使演示与评测共用一套基线。

**Non-Goals**

- 不做完整的代码级根因分析（只到文件与方法级线索）。
- 不做真实 CI 流水线插件（构建阶段介入不在本次范围）。
- 不做递归依赖追踪（跨项目仅一跳）。
- 不做多租户权限与隔离的安全模型（假定单团队内部使用）。
- 不做自动执行处置动作（只输出建议，不落地变更）。

## Decisions

### D1：单进程多租户，而非每项目一个 Agent 实例

```
        方案 A: 每项目一个进程          方案 B: 单进程 + 项目档案 ★
        ──────────────────────         ──────────────────────
        N 份部署、N 份升级              1 份部署
        主机指标被采集 N 次              主机指标全局一份
        无任何进程能看到全局             天然具备跨项目视角
```

选 B。决定性理由不是运维成本，而是能力边界：本变更最有价值的判断之一是"A 项目变慢的真实原因是 C 项目吃满内存"（见 `specs/fault-scenarios` 的资源争用场景）。方案 A 中每个实例的视野被物理限制在单项目内，这个结论无法产生。

代价是必须自行设计隔离边界，见 D3、D4。

### D2：项目档案用 YAML 文件声明，启动加载 + 显式重载

候选：YAML 配置文件 / 关系数据库 / 注解扫描自动发现。

选 YAML。项目数量在个位数，档案变更频率低于代码变更频率，配置文件可随代码进版本库、可 diff、可 review，这三点对演示与评测的可复现性比动态注册更重要。数据库方案引入 schema 迁移与初始化数据的额外成本，收益在当前规模下为零。

档案放在 `config/projects/<projectId>.yml`，通过 `application.yml` 中的目录配置指向。提供显式重载接口而非文件监听，避免半写入文件被加载。

档案结构（对应 `specs/project-registry` 的档案结构要求）：

```
ProjectProfile
├── identity      id / name / owner / port / tags
├── datasources
│   ├── logs      type(cls|file|es) · locator · fieldMap
│   ├── metrics   [{ name · promQL · threshold · meaning }]
│   └── code      repoPath · mainBranch · packagePrefix
├── knowledge     namespace · docRoots[]
├── business
│   ├── criticalPaths  [{ name · steps[] }]
│   └── knownFaults    [{ pattern · hint · runbookRef }]
├── dependencies  upstream[] · downstream[]
└── ops           alertLabels · severityMap · oncall
```

`packagePrefix` 用于从异常堆栈中筛出属于本项目的帧，是代码线索定位能落地的关键字段。

### D3：`projectId` 作为工具的显式参数，服务端二次校验

候选：显式参数 / `ThreadLocal` 隐式上下文 / 每项目动态注册一套工具 Bean。

选"显式参数 + 服务端校验"的组合：

- 显式参数让项目维度出现在工具调用记录里，报告的工具调用摘要与追踪才有意义，模型的错误选择也能被观测到。
- 但绝不信任该参数：工具内部先用请求上下文中的权威 `projectId` 校验，模型传入不一致或未注册的值时直接拒绝并返回明确错误（对应 `specs/scoped-data-access` 的拒绝查询要求），而不是回退到全局数据源。

排除动态注册每项目工具 Bean：工具数量随项目数线性膨胀，会挤占工具选择的上下文并显著降低选对工具的概率。

### D4：知识隔离用元数据过滤，不用独立集合

```
                metadata 过滤 ★       partition            独立 collection
  隔离强度       逻辑                  物理分区              物理
  跨项目检索     天然支持              需多分区查询          需多次查询合并
  平台通用文档   scope 字段即可        需额外分区            需额外集合
  迁移成本       补字段 + 重建索引      重建                 重建 + 写入改造
```

选元数据过滤。集合 schema 增加 `project_id` 与 `scope`（`project` / `platform`）两个标量字段，检索时按形态构造过滤条件：

- 项目级：`(project_id == <当前项目> AND scope == 'project') OR scope == 'platform'`
- 平台级：`scope == 'platform'`
- 跨项目参考（需显式开启）：放开 `project_id` 约束，结果标注来源项目

独立集合方案会把"其他项目遇到过同类问题吗"这个能力堵死，而这恰是知识沉淀的价值所在。

### D5：一套编排图 + 诊断形态分叉，而非两套 Graph

`SupervisorAgent` / `plannerAgent` / `executorAgent` 的拓扑不变，形态差异通过三个注入点实现：

```
   DiagnosisRequest(mode, projectId?)
              │
              ▼
   ┌──────────────────────┐
   │  DiagnosisContext     │  ← 装配：档案 + 形态 + 时间窗
   └──────────┬───────────┘
              │ 注入点 1：提示词变量
              │ 注入点 2：工具可见集
              │ 注入点 3：报告模板
              ▼
   ┌──────────────────────┐
   │  既有 Supervisor 编排  │  ← 拓扑不变
   └──────────────────────┘
```

- 注入点 1：提示词从硬编码字符串改为模板 + 变量。平台级注入受影响项目摘要与资源指标清单；项目级注入关键链路、已知故障模式、可用业务指标。
- 注入点 2：平台级不暴露项目日志查询工具，项目级不暴露跨项目检索工具（除非显式开启）。工具可见集是比提示词更硬的约束，用来兜住模型不遵守指令的情况（对应 `specs/diagnosis-modes` 的形态不串用要求）。
- 注入点 3：两套报告模板骨架，共用证据链与置信度规则。

两套 Graph 的方案会让 Supervisor 逻辑、重试策略、追踪埋点各维护一份，且资源争用场景需要形态中途切换时无法复用状态。

### D6：提示词统一模板 + 变量注入，保留单项目逃生舱

候选：每项目一份完整提示词 / 统一模板 + 结构化变量。

选后者。每项目一份提示词意味着评测基线要跑 N 套、提示词改进无法横向生效，随项目数增长会直接压垮 `specs/fault-scenarios` 的评测体系。业务语义作为结构化数据（关键链路、已知故障）注入模板，改一处全局生效。

保留 `business.extraPromptHint` 字段作为逃生舱，供个别特殊项目补充少量说明；该字段有长度上限，防止退化成"每项目一份提示词"。

### D7：跨项目扩展限定一跳，且必须留痕

一跳的判定入口是"日志证据指向已声明的下游依赖"，而非模型自由决定。扩展后在报告中显式标注扩展范围。

不做递归的理由是可终止性与成本：依赖图存在环时递归无法自然终止，且每跳都会带来一轮完整的指标 + 日志查询，token 与耗时随深度指数增长。二跳线索降级为"待确认线索"记录，由人工决定是否另起一次诊断。

### D8：代码定位止于文件与方法级

从日志异常堆栈中按 `packagePrefix` 筛出项目自身的栈帧，映射到 `repoPath` 下的文件与方法，并附带触发该线索的原始日志记录。无堆栈时不给位置。

不做完整代码根因分析：需要跨文件调用图与版本比对，实现成本与幻觉风险都远超收益。把边界写进 `specs/scoped-data-access` 的规格里，是为了让"不越界"成为可验收的行为而不是口头约定。

### D9：故障注入用进程内可控端点 + 编排脚本

候选：外部混沌工程工具 / 被监控项目内置注入端点。

选内置端点。八个场景中有六个需要产生特定的业务指标变化与特定格式的错误日志（例如"关键链路第三步失败"），外部工具只能施加资源压力，无法精确制造业务语义层面的故障。内置端点还天然满足 `specs/fault-scenarios` 的可撤销要求。

主机资源类场景（内存、磁盘）由独立的压力脚本施加，与业务注入解耦。

演示项目取三个且职责不对称：一个主角项目（承载业务类场景，日志最完整）、一个下游项目（承载依赖故障场景）、一个配角项目（仅用于验证切换与资源争用，可极简）。

### D10：报告与场景执行结果先落轻量存储

采用内嵌数据库存储报告、反馈与场景执行记录，报告正文以结构化文档形式保存。选内嵌而非外部数据库，是为了保持单机演示可一键启动。

报告一经生成即不可变（对应 `specs/diagnosis-report` 的不可静默改写要求），更新走"新报告 + 关联旧报告"的方式。

### D11：时间对齐统一在服务端完成

各数据源时间基准不一致（Prometheus 为秒级 UTC、日志为毫秒级带时区、变更事件为提交时间），全部在装配 `DiagnosisContext` 时归一到统一时区与统一时间窗，模型只看到归一后的时间轴，并保留各事件的原始精度标记。

不把时间换算交给模型：跨时区与精度推断是模型高频出错的地方，且错误会静默传播到时间线与因果判断上。

### D12：上下文压力集中在工具返回，摘要在服务端完成

诊断类 Agent 的上下文膨胀几乎全部来自工具返回——一次日志查询可能命中上千条记录，而指标与变更的返回量是可控的。因此压缩的重点不是对话历史，而是工具返回。

摘要在服务端完成而非交给模型：让模型先读全量再自行总结，等于污染已经发生。服务端在工具返回进入上下文前按类型聚合——日志按错误签名分类并给出出现次数、时间分布与代表性样本，指标按时间窗降采样。

```
   工具原始返回                服务端摘要                进入上下文
   ─────────────              ─────────────            ─────────────
   1200 条 ERROR 日志    →    3 类错误签名             ~800 token
   ~150k token                各自次数/时间分布
                              每类 2 条代表样本
                              + 回查定位信息
```

摘要必须保留回查定位信息（时间范围、条数、关键标识），否则报告的证据链无法溯源到原始记录，与 `specs/diagnosis-report` 的可追溯要求冲突。

记忆分三层：会话短期记忆、单次诊断轨迹、长期知识。诊断轨迹不跨次复用，理由与 D7 同源——历史轨迹进入新诊断会让模型倾向复述旧结论而跳过取证，这是幻觉的常见来源，故在 `specs/context-memory` 中把"记忆不得替代取证"写成硬要求。

这三层是可见边界，不是工作记忆的实现形态。单次诊断的工作记忆落地为 **证据黑板（Evidence Blackboard）**：每轮只把黑板摘要与本步工具摘要交给模型，避免把诊断做成「越来越长的聊天记录」。这与编码 Agent 的 feature list 同构，但载荷是告警、证据、假设与 `rawRef`，而不是功能清单。

形态层再加一道上下文防火墙：平台级以共享资源与受影响项目摘要为主，单项目业务日志只能作为范围证据；项目级绑定当前档案，切换项目时清空业务证据区。跨次复用的唯一通道是采纳后的知识沉淀，检索命中也只能当 `historical_clue`。

Token 预算在本系统里同时是置信度机器：耗尽时输出部分结论并显式标注，发生裁剪则置信度不得为高。静默截断会产出一份看起来完整、实则证据不全的报告，比明确失败更危险。

### D13：三处埋点，轨迹与业务指标分离

在 Graph 节点流转、LLM 调用、工具调用三处埋点。选这三处是因为它们恰好覆盖了诊断失败的三类原因：编排逻辑走错、模型输出不可用、数据取不到。

轨迹（逐次事件明细）与指标（聚合数值）分开处理：轨迹落库供按追踪标识回放，指标经 Micrometer 暴露给既有的 Prometheus 链路。不把轨迹也做成指标，是因为轨迹的基数太高（每次调用的参数各不相同），做成标签会导致时间序列爆炸。

提示词与响应正文的留存做成可配置。开启便于调试提示词，关闭可控制存储增长；但无论开关如何，模型标识、Token、耗时、成败这些结构化字段必须保留，否则成本观测直接失效。

被服务端校验拒绝的工具调用也要记录（对应 `specs/agent-observability`）。这类记录是观测"模型有多经常选错工具"的唯一数据来源，也是评估工具描述质量的依据，丢掉就失去了优化工具设计的反馈。

埋点异步写入且失败不影响主流程：可观测组件不应成为诊断可用性的新单点。

### D14：知识沉淀经人工确认，不做全自动回写

候选：采纳即自动写入知识库 / 采纳生成候选、人工确认后发布。

选后者。自动回写有两个无法接受的后果：一是采纳只代表"这次结论看起来对"，不代表它足以作为通用处置知识，直接入库会让一次误判永久污染后续所有同类检索；二是采纳频率高于知识更新的合理频率，自动写入会迅速堆满同质文档，稀释检索质量。

去重走相似度阈值判定，超过阈值转为更新已有文档而非新增，并保留历史版本标识。这是防止知识库退化为流水账的关键——检索 top-k 有限，同质文档会挤占本该属于其他知识的位置。

驳回不产生知识，但驳回原因要可汇总，并尽量关联到场景库中的对应场景。这条把 `specs/knowledge-evolution` 与 `specs/fault-scenarios` 连了起来：真实使用中的失败模式可以反过来补充评测基线，而不只是停留在最初设计的八个场景。

## Risks / Trade-offs

- **模型忽略项目边界，跨项目串味** → 边界不靠提示词兜底：工具层用权威 `projectId` 二次校验并拒绝越界查询（D3），知识层用过滤条件在检索侧切断（D4），形态层用工具可见集限制（D5）。三层都是服务端强制。

- **提示词注入档案内容导致 token 膨胀** → 只注入语义摘要（关键链路步骤名、已知故障模式条目），正文留在知识库按需检索；`extraPromptHint` 设长度上限；随项目档案增长需监控单次诊断的 token 用量。

- **Milvus 集合 schema 变更需要重建，历史文档丢失归属** → 迁移期间保留旧集合只读；重建时按文档所在目录批量补写 `project_id` 与 `scope`；无法判定归属的文档统一标为 `platform` 并人工复核。

- **单进程承载多项目，一次诊断拖垮全局** → 诊断请求设置总时长与工具调用次数上限；并发诊断做数量限制；单项目档案校验失败不影响其他项目（已写入 `specs/project-registry`）。

- **资源争用场景需要形态中途切换，状态管理复杂** → 该场景以"平台扫描先行"的方式规避中途切换：模糊归属时先做一轮轻量平台扫描再定形态（见 `specs/diagnosis-modes`），扫描结果作为上下文传递，不做真正的运行中形态切换。

- **演示环境资源不足以同时跑三个项目 + Milvus + Prometheus** → 配角项目做到极简（仅产生日志与少量指标，不承载真实业务逻辑）；资源类场景注入设定安全阈值，避免把开发机压到不可用。

- **置信度标注流于形式，模型倾向一律给高置信度** → 置信度不完全交给模型：证据完整性由服务端统计（关键数据源是否失败、是否命中知识文档、是否有代码线索），据此设置置信度上限，模型只能在上限内评估。

- **八个场景过拟合，掩盖真实泛化能力** → 场景库区分"演示集"与"保留集"，保留集不参与提示词调优；每次提示词改动后在保留集上复跑，观察是否出现只在演示集上生效的改进。真实使用中的驳回记录关联回场景库（D14），持续补充最初设计未覆盖的失败模式。

- **摘要丢失关键信息导致根因判断偏差** → 摘要保留回查定位信息，报告中的每条日志证据都能溯源到原始记录；摘要策略本身纳入保留集评测——若某场景因摘要丢失线索而判定未通过，说明聚合维度需要调整。

- **轨迹数据随诊断次数增长膨胀** → 轨迹与指标分离（D13），高基数明细落库而非做成时间序列；提示词正文留存可关闭；轨迹设置保留期，超期清理但保留其汇总指标。

- **人工确认环节成为知识沉淀的瓶颈** → 候选知识自动完成结构化，确认环节只需审阅与微调而非从零撰写；相似候选走更新路径（D14），减少需要确认的条目数量。

## Migration Plan

分阶段推进，每阶段结束系统均可运行、可演示。

```
 阶段 1        阶段 2        阶段 3        阶段 4        阶段 5        阶段 6
 档案与路由 → 形态与上下文 → 知识与沉淀 → 报告与观测 → 场景与评测 → 前端与打磨
 ─────────    ──────────    ─────────    ─────────    ─────────    ─────────
 单项目跑通    两形态可用     跨项目不串味  轨迹可回放    八场景可复现  切换器+报告页
              上下文受控     采纳可沉淀    成本可观测    保留集基线    候选确认入口
```

1. **档案与路由**：引入档案结构与注册表，工具层加 `projectId` 参数与校验。此阶段先注册一个项目，行为与现状等价，用于验证路由链路。
2. **形态与上下文**：拆分平台级与项目级入口，提示词改模板化注入；同期落地证据黑板、形态防火墙、工具返回溯源摘要与 Token 预算——上下文机制必须与提示词改造一起做，否则模板化后的上下文结构会被推翻重来。
3. **知识与沉淀**：Milvus schema 变更与数据重建，检索加过滤条件与跨项目开关；建立候选知识生成与确认发布链路。
4. **报告与观测**：落地结构化报告与置信度规则；同期完成三处埋点、轨迹落库与运行指标暴露——报告中的工具调用摘要本就依赖轨迹数据，两者共用同一份记录。
5. **场景与评测**：接入演示项目与注入端点，落地八个场景与判定逻辑，建立执行记录与保留集跑批。
6. **前端与打磨**：项目切换器、平台层/项目层双视图、报告页时间线与证据链展开、采纳/驳回与候选知识确认入口。

**回滚策略**

- 阶段 1 至 2 通过配置开关退回单项目模式：注册表仅含一个项目且形态固定为项目级，行为回到现状。上下文摘要与 Token 预算通过阈值配置关闭，退回全量注入。
- 阶段 3 的 Milvus 变更风险最高，迁移期保留旧集合，检索层通过开关切回旧集合；知识沉淀链路可单独停用，已发布文档不受影响。
- 阶段 4 的可观测埋点为旁路设计，停用后不影响诊断主流程，仅报告中的工具调用摘要退化为空。
- 阶段 5 至 6 为增量新增，直接停用对应入口即可回滚。

**兼容性处理**

现有 `prometheus.mock-enabled` 与 `cls.mock-enabled` 双模保留，但语义下沉：全局开关决定是否启用模拟数据源，具体数据源仍由档案解析。这样评测可在全模拟环境下复现，演示可在真实环境下进行。

## Open Questions

- 报告与执行轨迹的保留期限与清理策略（不影响接口与任务拆分，可在阶段 6 依据实际数据量确定）。
- 工具返回摘要的具体聚合维度与阈值（日志按错误签名分类的粒度、代表性样本条数），需依据保留集跑批结果调优，不影响模块划分。
- 候选知识去重的相似度阈值取值，需依据实际沉淀数据校准。
- 演示项目最终选用的业务隐喻（发卡、下单或其他），仅影响场景命名与文案，不影响档案结构与判定逻辑。
